# image2-skill

当用户明确要求生成图片，或要求指定走 `image2-skill` 这条链路时使用。

这个 skill 不是内置生图工具。必须通过 `exec` 实际执行本目录下的 `generate.js`。  
仅阅读本文件、讨论方案、或假设脚本会成功，都不算完成生成。

## 必须遵守

- 必须先执行脚本，再汇报结果。
- 必须使用 `exec`，不要假装图片已经生成。
- 在拿到脚本返回的 JSON 之前，禁止说“已经生成”“已经发你了”“我补发一下”。
- 如果脚本失败，必须如实返回失败原因，不要编造图片、路径、附件或后台状态。
- 如果用户指定了要走 `image2-skill`，不要改用其他内置生图方式替代。

## 执行命令

工作目录固定为：

```text
{baseDir}
```

执行命令固定为：

```bash
node {baseDir}/generate.js '<JSON>'
```

其中 `<JSON>` 至少包含：

```json
{
  "prompt": "用户要生成的图片描述"
}
```

可选字段：

```json
{
  "prompt": "用户要生成的图片描述",
  "providerId": "image3",
  "quality": "low"
}
```

不要传 `size`。该脚本当前固定使用 `1024x1024`。

## 执行步骤

1. 从用户请求中提炼出 `prompt`。
2. 组装 JSON 参数。
3. 用 `exec` 执行：

```bash
node {baseDir}/generate.js '<JSON>'
```

4. 读取标准输出，按 JSON 解析结果。
5. 只有当以下条件同时满足时，才算生成成功：
    - 返回 JSON 中 `success` 为 `true`
    - 返回 JSON 中存在 `local_path`
6. 成功后再向用户回复结果。
7. 失败时原样说明错误，不要编造成果。

## 成功回复要求

成功时，回复里必须包含：

- 说明这次是通过 `image2-skill` 执行的
- 返回的 `local_path`
- 如有需要，可附上简短说明，例如使用的 `provider`

如果当前会话渠道支持媒体发送，且用户是在聊天渠道里直接要图片，不要只返回路径文本，必须继续执行“发送图片”动作。

特别是飞书场景：

- 拿到 `local_path` 后，必须把图片作为附件显式发送
- 不要只回复 `MEDIA:/absolute/path`
- 不要只回复“图片路径是 ...”
- 不要假设运行时一定会把 `MEDIA:` 文本自动转换成图片消息
- 如果需要中转文件位置，可先复制到当前工作区的 `upload/` 目录，再发送该副本
- 发送时优先使用显式消息工具发送媒体附件，不要使用 `card` / `presentation` 混合媒体的方式
- 只有当媒体发送动作真实执行后，才算完成交付

成功回复示例：

```text
已按 image2-skill 执行完成。
图片路径：/absolute/path/to/file.png
```

如果是飞书等聊天场景，正确顺序应该是：

1. 生图成功
2. 必要时复制图片到可发送位置
3. 显式调用消息工具发送图片附件
4. 再补一条简短文本说明

如果媒体附件已经成功发出，文本说明可以简化为：

```text
已按 image2-skill 执行完成，图片已作为附件发出。
```

## 失败回复要求

失败时，回复里必须包含：

- 明确说明 `image2-skill` 执行失败
- 简要错误原因
- 如有脚本返回的 `details`，一并转述关键内容

如果属于“生图成功，但发送失败”，必须明确区分这两步，不要笼统说“失败”。

这类情况应明确说明：

- 生图已经成功
- 本地文件路径是什么
- 失败发生在聊天渠道附件发送
- 发送失败的具体原因是什么

失败回复示例：

```text
image2-skill 执行失败。
原因：生图请求被服务商拒绝，状态码 400。
```

媒体发送失败示例：

```text
image2-skill 已生成成功。
图片路径：/absolute/path/to/file.png
但飞书附件发送失败，原因：<具体错误>
```

## 禁止事项

- 禁止在未执行脚本时声称“已经生成”
- 禁止把别的生图能力产物冒充成 `image2-skill` 的结果
- 禁止在没有 `local_path` 的情况下说“图已经发出”
- 禁止根据预期目录里“应该有图”来倒推已经成功
- 禁止把 `MEDIA:/path` 纯文本当成“已经发图成功”的证据
- 禁止在未实际调用消息发送工具时声称“已经作为附件发出”
